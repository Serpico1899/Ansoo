# ADR-0001: v3.1 Is the Single Canonical Domain Baseline

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-11-16 |
| Owners | Product owner, backend owner |
| Supersedes | v1.0 (fa), v2.0 (en), `CONSUMER_TRANSPARENCY_FINAL_ERD.md` as domain authority |
| Superseded by | none |

## Context

The repository contained two competing domain baselines:

- `CONSUMER_TRANSPARENCY_FINAL_ERD.md`, used by the scaffold, the summary, plan 01, and the architecture
  spike report.
- `CONSUMER_TRANSPARENCY_DOMAIN_SPEC_v3.1.md`, which declares itself canonical and supersedes v1/v2 in full.

They disagree on material model boundaries: categories, the number of Lesan relations, relationship
predicates, claim types, visibility scope, source snapshot versioning, findings governance, public profile
assembly, and acquisition work. Keeping both as authority would guarantee contradictory code.

The spike (plan 01) was executed against the older baseline. Its Lesan/MongoDB mechanics are still valid,
but some of its domain decisions are not.

## Decision

`CONSUMER_TRANSPARENCY_DOMAIN_SPEC_v3.1.md` is the only authoritative domain contract. Code, validators,
tests, projections, and plans follow it. Any conflict with another document is resolved in favor of v3.1.

The following v3.1 changes take effect immediately in planning and in any new code:

| Area | v3.1 decision | Old baseline effect |
|---|---|---|
| Collections | Exactly 11 core collections; no `categories` | `categories` and its actions are removed/deferred |
| Product category | `categoryCode: string` + `taxonomy.v1.json` | No Category model, no `Product.category` relation |
| Lesan relations | Exactly 2: `Product.brand`, `SourceSnapshot.source` | Third relation (`Product.category`) is void |
| Predicates | Exactly 5: `OWNS`, `CONTROLS`, `MANUFACTURES`, `DISTRIBUTES`, `IMPORTS_TO_MARKET` | `SUBSIDIARY_OF`, `OPERATES`, `SUPPLIES`, `EXPORTS_TO_MARKET`, `LICENSES`, `FRANCHISES` removed/deferred |
| Claim types | Exactly 3: `MARKET_PRESENCE`, `PRODUCT_ORIGIN`, `OFFICIAL_STATEMENT` | Other claim types and `OTHER_*` removed |
| Publication | `visibilityScope` removed | Access is enforced by roles and server-side projections only |
| Source | No `latestSnapshotId`; no snapshot `version` | `lastCapturedAt` plus bounded reverse preview only |
| Product attributes | Typed array with a small registry | Free-form `Record<string, unknown>` removed |
| Governance | `sensitivity`, `publicationGate`, right of reply, four-eyes, merge/redirect, redaction lineage, idempotency | v3/v3.1 additions are mandatory |
| Public profile | Explicit assembly contract + `product_public_profiles` read model | New required subsystem |
| Acquisition/research | Data acquisition and research operations are in scope, equal priority | Cannot be treated as an appendix |

The eleven collections are:

```
products, brands, organizations, relationships, claims, sources,
source_snapshots, assets, corrections, users, audit_events
```

## Alternatives Considered

1. **Keep the old ERD as authority and treat v3.1 as a proposal.** Rejected: v3.1 explicitly supersedes it,
   and the old baseline contradicts several non-negotiable invariants (categories scope, predicate/claim
   enumeration, snapshot versioning).
2. **Merge both documents into a compromise baseline.** Rejected: it would reopen LOCKED decisions and
   produce an unbounded modelling debate instead of a contract.
3. **Rewrite the spike against v3.1 before planning.** Rejected as a prerequisite: the spike's Lesan/MongoDB
   observations are still usable. A short alignment plan (plan 02) records which spike conclusions survive
   and which are void.

## Consequences

- Plan 01, prompt 01, and report 01 are marked historical where they touch domain decisions. Their
  infrastructure and Lesan findings remain evidence.
- `summary.md` is rewritten to v3.1 and must not be used to reintroduce old fields.
- The scaffold's `models/category.ts` and `src/category/` are stale and must be removed or explicitly
  archived by plan 02.
- `Product` and `SourceSnapshot` model boundaries change: one optional and one required Lesan relation.
- Any future change to the eleven collections, two relations, five predicates, three claim types, or
  fifteen invariants requires a new ADR.
- The six open questions in spec Section 22 remain open; this ADR does not answer them.
